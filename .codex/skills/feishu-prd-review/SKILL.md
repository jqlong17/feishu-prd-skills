# 飞书 PRD 评审

对一篇已经写好的飞书 PRD 做独立评审。评审结论只来自文档正文、表格和截图，不来自写作过程里的对话。

先读本 skill，再读同目录的 `rubric.md`。需要改文档时才读撰写 skill `feishu-prd`。评审本身不改文档。结构对照仓库根目录的 `examples/reference-prd.md`，不要把范例里的业务对象写进所评文档。

## 何时用

- 用户要评审、打分、找遗漏、看边界清不清楚
- 用户给出飞书 PRD 链接或 document id

不要在用户只是要求改某一句时启动整篇评审。

## 独立评审

1. 用 `lark-cli docs +fetch --as user --detail with-ids` 读全文。大纲不够就按章节再读。
2. 不向作者追问「你是不是这个意思」来抬分。文档没写的，就记为未写。
3. 截图只看文档里的图和 caption，不把本地未贴进文档的页面算进去。
4. 对话、注释、本期不做，都不能填补主流程上的空洞。
5. 评完只输出评审。用户没有要求改文档时，不调用 `docs +update`。

## 这篇 PRD 的体例

评审时按下面的成品标准，不按「有没有写产品策略」加分。

- 结构是：基本信息、版本记录、需求背景（现状 / 目标 / 用户旅程）、需求详情、本期不做、验收标准、未来版本。
- 需求详情按用户使用顺序写，用 4.1、4.2.1 这种编号。一条路径里的两种做法要分成并列小节，各自有说明和截图。
- 页面上的列表要写清字段、显示规则和限制，用表格，不把字段散落在形容词里。
- 只写上线后的行为。不写产品策略、待确定、上线前/上线后对照，也不写「没有某按钮」「不能收起」这类非需求。
- 图按阅读顺序连续编号。图注是「图 N …」，图下单独一行「线上demo入口：」加可打开的线上地址。地址不写 localhost，也不写 `shot=`、`preview=` 这类内部演示参数。上一节已经写清这一步时，不要求图前再重复一段。
- 平台原有能力只写本期怎么用到它。不要求把原有页面的字段再列一遍。
- 正文用肯定句写谁能做什么、数据范围、失败时怎样。不解释这篇文档为什么这样写。

## 评审顺序

1. 抽出一条主路径：角色从进入到得到结果，逐步列出文档里的动作。
2. 对照需求详情，标出路径上没写输入、没写系统结果、没写失败、或下一步接不上的位置。
3. 把用户旅程、需求详情、验收标准三处对一遍。旅程里有、详情没有，或详情有、验收没有，都算遗漏。
4. 再按 [rubric.md](rubric.md) 的五个维度打分。每个扣分都要指向具体段落或图号。
5. 每个维度给出修改意见。意见必须成对出现：先摘文档里的原句，再写建议改成的整句。不写「可以更清晰一些」这种没有替换文本的话。

## 打分

满分 100。五个维度分数相加。

| 维度 | 满分 | 看什么 |
| --- | --- | --- |
| 边界是否清晰 | 30 | 谁、范围、默认、禁止、失败 |
| 整体串联 | 20 | 主路径不断、旅程和验收对得上 |
| 特殊情况 | 25 | 空、重名、部分失败、未维护、越界 |
| 截图是否完整 | 15 | 每一步可见界面都有图，且和正文一致 |
| 语言是否大模型风格 | 10 | 像同事写的需求，而不是模型在解释写法 |

总分含义：

- 90–100：可以拿去评审，只需改个别句子
- 75–89：主路径能读完，但边界或特殊情况还有洞
- 60–74：研发会靠猜实现
- 60 以下：先补主路径和边界，再评文字

边界或整体串联低于该维度满分的 60% 时，总分再注明「不建议进入评审」，即使其他项很高。

## 输出

用中文，按这个结构，不要先写总评套话。

```markdown
# PRD 评审：{文档标题}

文档：{链接}
总分：{n} / 100
结论：{可以进入评审 / 补完边界后再评 / 不建议进入评审}

## 主路径
1. …
断点：{没有则写「主路径可以串完」}

## 分项
### 边界是否清晰　{n}/30
扣分：
- {位置}：{缺的边界}（扣 {n} 分）
修改：
- 原文：「{从文档复制的原句；整段缺失时写：未写}」
  建议改为：「{可以直接替换进去的整句或表格单元格}」
  放在：{章节号或图号前后}

### 整体串联　{n}/20
### 特殊情况　{n}/25
### 截图是否完整　{n}/15
### 语言是否大模型风格　{n}/10

## 优先改这三处
1. 原文：「…」建议改为：「…」

## 修改意见
每次评审在分项之后必须再输出这张表。没有这张表，评审不算完成。表内每一行都是一条可以单独改的意见，编号从 1 连续编排。作者之后只回编号，就按该行的「建议修改后」改文档。

| 编号 | 原文 | 建议修改后 | 理由 |
| --- | --- | --- | --- |
| 1 | 「{文档原句；整段没有则写：未写}」 | 「{可原样贴回的整句、表格单元格或图注}」 | {为什么改，放在哪一节} |
```

五个维度都要按上面的格式写满「扣分」和「修改」。没有扣分时，扣分写「未扣分」，修改写「无」。分项里的修改意见必须同时出现在文末这张表里，不另写一套说法。

修改意见的写法：

- 「原文」必须是文档里的原句，用引号包住。不要改写、不要概括。
- 「建议改为」必须是替换后的完整句子或表格单元格，作者可以原样贴回文档。
- 某条行为完全没写时，原文写「未写」，建议改为给出要新增的整句，并写明插在哪一节、哪一句后面。
- 截图问题同样成对写。原文摘图注或图前那句说明；建议改为写应补的图注、图前说明，以及这一帧要看到的界面状态。
- 禁止只写「建议补充边界」「建议增加截图」「表述可以更具体」。没有替换文本的意见不算完成。
